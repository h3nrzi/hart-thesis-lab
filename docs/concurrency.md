# سیاست چند ایجنت و چند سشن

گفتگوی هر ایجنت موقتی است؛ Git منبع حقیقت است. این نسخه **همزمانی را با PR و بررسی تعارض مدیریت می‌کند**؛ قفل مرکزی یا محافظت اجباری شاخه در تنظیمات GitHub هنوز به‌صورت مستقل فعال نشده است.

## هر تغییر
۱. قبل از نوشتن `git fetch origin main` و وضعیت آخرین `origin/main` را ببین؛ اگر فایل محلی تغییرات ثبت‌نشده دارد، **توقف** و از کاربر تعیین تکلیف بخواه (بدون reset).
۲. از HEAD تازه، یک شاخه کوتاه‌عمر `agent/<idea-id>/<action>-<unique>` بساز. هر PR فقط یک عملیات پرونده را تغییر بدهد.
۳. قبل از نوشتن: `python3 scripts/agent_status.py --id <id>`؛ اگر حالت مورد انتظار نبود، توقف. متن مرجع فقط داده ارسالی کاربر است.
۴. پس از نوشتن: تست و اعتبارسنجی، Commit، PR. قبل از ادغام مطمئن شو پایه PR همچنان تازه است؛ اگر عوض شده، بازخوانی پرونده و rebase محافظه‌کارانه یا PR جدید. **کپی‌کردن کورکورانه فایل قدیمی روی HEAD جدید ممنوع است.**
۵. قبل از ادغام، GitHub Actions باید سبز باشد. نیاز به فعال‌سازی Branch Protection توسط صاحب مخزن برای الزام PR/CI وجود دارد.
۶. هرگز force-push، amend مشترک، حذف/بازنویسی original/update/review یا push هم‌زمان مستقیم main نکن.

## برخورد دو سشن با همان پرونده
- سشن A و B هر دو از یک HEAD شروع می‌کنند.
- A پرونده را ایجاد/به‌روز می‌کند؛ B هنگام تازه‌سازی HEAD باید وضعیت تازه را **دوباره** محاسبه کند.
- اگر B همان مدرک را می‌آورد: فقط به سند موجود ارجاع بده؛ فایل دوباره نساز.
- اگر B یک مدرک جدید دارد: شاخه/PR جدید از HEAD تازه؛ نام رویداد یکتا.
- اگر دو نتیجه ناسازگار ادعا می‌شوند: حالت `CONFLICT` و توقف؛ تصمیم با شواهد و کاربر.

## محدودیت کنترل فنی
اسکریپت `scripts/check_change_policy.py` در CI بازنویسی فایل‌های تاریخی را در محدوده diff رد می‌کند؛ این با Branch Protection ترکیب شود. روی مخزن بدون محدودیت ادغام، هیچ AGENTS.md یا CI نمی‌تواند کاربری با دسترسی write را از دور زدن قوانین بازدارد. تعارض‌های مفهومی شواهد نیز نیازمند بازبینی انسانی‌اند.
