# سیاست چند ایجنت و چند سشن

حافظه گفتگوی هر ایجنت موقتی است؛ Git و پرونده‌های نسخه‌بندی‌شده منبع حقیقت هستند. هم‌زمانی از طریق شاخه‌های جدا، PR و بررسی تعارض مدیریت می‌شود. **فایل‌های موقت نادیده‌گرفته‌شده در .gitignore، تغییرات پرونده نیستند.**

## بررسی امن پیش از هر تغییر

۱. از آخرین `origin/main` با `git fetch origin main` مطلع شو؛ `git status --short` را بخوان و سپس **کنترل استاندارد و فقط‌خواندنی** را اجرا کن:

```bash
python3 -B scripts/check_worktree.py
```

۲. اگر `clean: true` و `next_action: proceed` بود، تغییرات مربوط به همین عملیات را در شاخه جدید شروع کن. **وجود فایل ignored مانند `scripts/__pycache__/` مانع نیست، نیازی به حذف ندارد و مجوزی برای پاک‌سازی آن وجود ندارد.**

۳. اگر `clean: false`، دستور Git خطا، فایل غیرignored ناشناخته یا تغییر واقعی در فایل نسخه‌بندی‌شده وجود داشت، **توقف و گزارش**. نه آن فایل را حذف کن، نه `reset --hard` یا `git clean` بزن؛ برای تعیین تکلیف از کاربر اجازه بگیر.

۴. برای وضعیت‌خوانی، Python را با `-B` اجرا کن تا فایل بایت‌کد جدید تولید نشود:

```bash
python3 -B scripts/agent_status.py
python3 -B scripts/validate_structure.py
```

۵. اگر وضعیت تمیز است، از HEAD تازه یک شاخه کوتاه‌عمر `agent/<idea-id>/<action>-<unique>` بساز. هر PR فقط یک عمل مربوط به پرونده را تغییر دهد. پیش از نوشتن `python3 -B scripts/agent_status.py --id <id>` و مرحله مورد انتظار را بررسی کن.

۶. بعد از تغییر، آزمون‌ها، اعتبارسنجی، Commit و PR؛ پیش از ادغام تازه‌بودن مبنای PR را بررسی کن. در صورت تغییر HEAD از ابتدا پرونده را بخوان. ادغام کورکورانه فایل قدیمی روی HEAD تازه ممنوع است.

۷. GitHub Actions باید قبل از ادغام سبز باشد. فعال‌سازی Ruleset یا Branch Protection برای الزام PR و CI هنوز اقدام مستقلی توسط صاحب مخزن است. هرگز `force push`، `reset --hard`، بازنویسی original/update/review یا push مستقیم main انجام نده.

## برخورد دو سشن با همان پرونده

- A و B ممکن است از یک HEAD شروع کنند؛ بعد از Commit/PR سشن A، سشن B باید HEAD و مرحله را دوباره محاسبه کند.
- مدرک تکراری = ارجاع به سند موجود، نه ساخت نسخه دوم.
- مدرک جدید = شاخه/PR تازه؛ نام رویداد یکتا.
- دو ادعای متعارض = وضعیت `CONFLICT` و توقف، نه انتخاب حدسی.

## حد مجوزِ نادیده‌گرفتن

`.gitignore` فقط برای خروجی‌های شناخته‌شده و قابل بازتولید است. **هر فایل ناشناخته، فایل متن/تحلیل، اسکریپت، یا تغییر در پرونده‌های tracked/untracked که Git گزارش می‌کند همچنان مانع است**. ایجنت حق ندارد برای دور زدن توقف فایل‌ها را به `.gitignore` اضافه کند یا آن را تغییر دهد.

کنترل `scripts/check_change_policy.py` بازنویسی اسناد تاریخی را در diff رد می‌کند؛ بدون Branch Protection قواعد را می‌توان توسط نویسنده صاحب مجوز دور زد و هنوز بازبینی انسانی ضروری است.
